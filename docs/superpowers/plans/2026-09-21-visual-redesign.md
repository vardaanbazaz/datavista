# DataVista Visual Redesign Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: superpowers:executing-plans (inline execution, not subagent-driven — verification here is a human/agent visually inspecting a real screenshot after each stage, which a dispatched subagent cannot do reliably). Steps use checkbox (`- [ ]`) syntax for tracking. **No `git commit`/`git add`/`git push`** at any step — CLAUDE.md forbids commits by this tool and the user explicitly said "No git add/commit/push." Stage boundaries end in a screenshot + report, not a commit.

**Goal:** Roll out DataVista's new visual design direction (confirmed via Figma: Foundations + Overview mockup) — a bold 3-tier maroon/near-black/gold palette, Inter + JetBrains Mono type system — across the app in verified stages, without touching application logic.

**Architecture:** Token layer first (Tailwind config + CSS custom properties + shadcn primitive variants), then typography, then a component-by-component visual pass starting with the highest-risk untested surface (DataTable), verified with real Playwright screenshots at each stage boundary.

**Tech Stack:** Vite + React + TypeScript, Tailwind CSS 3, shadcn/ui (Radix primitives), Playwright (`npm run test:e2e`, dev server on `localhost:8080`).

**Spec:** design brief pasted into conversation 2026-09-21 (exact hex/type-scale values below are transcribed verbatim from it — not re-derived).

## Global Constraints

- Styling/tokens/component-presentation only. Never touch state, data logic, business logic, or component behavior/props (exception: the in-flight unrelated AI Co-Pilot search-query change on `Dashboard.tsx`/`Sidebar.tsx`/`GlobalSearchModal.tsx`/`CommandPalette.tsx`/`OnboardingTour.tsx` is pre-existing uncommitted work, not part of this task — do not touch those diffs, do not revert them, style around them normally when those files come up in a later component pass).
- Exact colors: Background `#0A0B10`, Surface `#13151C`, Surface Elevated `#1A1D26`, Border Subtle `#262A35`, Border Default `#333846`, Text Primary `#F4F5F7`, Text Secondary `#A3A9B7`, Text Tertiary `#6B7280`, Main `#7C2438`, Secondary (near-black) `#0D0C0B`, Tertiary `#D4AF37`, Success `#22C55E`, Danger `#F55A4E`.
- Main is bold/generous (solid fills on active/selected), not just tints. Tertiary gold is sparse — reserve for AI-related UI and genuinely special highlights, never a general accent.
- Fonts: Inter (chrome) + JetBrains Mono (numeric/data values only: KPI numbers, table numeric columns, stat/pivot values). Self-hosted (offline-first constraint) — no Google Fonts CDN link.
- Type scale (size/line-height/weight): Display 32/40 Bold, H1 24/32 SemiBold, H2 18/26 SemiBold, H3/Label-lg 15/22 SemiBold, Body 14/20 Regular, Caption/Label 11/16 Medium uppercase +6-8% tracking, Data-Large(KPI) 28/32 JetBrains Mono Bold, Data-Table 14/20 JetBrains Mono Medium.
- ReactBits: 1-3 low-frequency spots max (empty-state illustration / onboarding / AI Sparkles detail). Never behind/around a chart, DataTable, or anything re-rendering on filter/interaction. When in doubt, skip it.
- Verify every stage with a real Playwright screenshot (`tests/e2e`, existing pattern) of the actual running app — not "should look right." Report back after each stage before moving to the next.

## Decisions Locked Before Implementation

1. **Light mode:** `index.css` currently ships a full light `:root` theme and `Sidebar.tsx` renders `<ThemeToggle>`; the brief supplies only one (dark) palette. Toggle removal is app-logic/product scope, not styling scope — out of bounds here. Resolution: the new tokens become the `.dark` theme (and `.dark` stays the default `<html>` class, unchanged from today), light `:root` keeps its existing neutrals as-is for now. Flagged to the user as a gap the brief doesn't cover, not silently decided away.
2. **Global zinc-scale lever:** grep shows hundreds of components use raw Tailwind `zinc-*`/`gray-*` utility literals (e.g. `dark:bg-zinc-900`), not the shadcn semantic tokens (`bg-background`, `bg-card`, etc). Stage 1 overrides Tailwind's built-in `zinc` color scale (in `theme.extend.colors`, which layers on top of — doesn't replace — the default palette) to the new neutral values, so the dark-mode app repaints in one file before any component is touched. This does not satisfy "shadcn default zinc/slate token references fully replaced" by itself — later component-pass stages replace raw `zinc-*`/`dark:zinc-*` literals with the named semantic tokens as each component is visited. `gray-*` is left untouched.
   - **Audited blast radius (post-hoc, at user's request):** 165 usages of `zinc-600..950` across 13 files. 99 (shades 700/800/900/950) are `dark:`-gated — dark mode only, no light-mode risk. **66 usages across 12 files are bare literals with no `dark:` prefix** (`text-zinc-700`/`900`, gradient `from-/to-zinc-900/600`, etc — used as the light-mode-side value next to a separate `dark:` override) and therefore do touch light mode: luminance drops ~32-34% at shades 600/700, ~26% at 800, ~13% at 900 vs stock Tailwind zinc, all staying inside the same dark-gray/near-black band (no contrast-safety break, no washout — a cooler/darker tint on already-dark light-mode text/icons). **User-confirmed tradeoff:** accepted for now rather than reverted or hand-scoped — all 12 affected files (`Dashboard.tsx`, `DashboardSummary.tsx`, `Sidebar.tsx`, `WelcomeOverlay.tsx`, `DataTable.tsx`, `KPICard.tsx`, `PivotTable.tsx`, `CommandPalette.tsx`, `AiSettingsModal.tsx`, `ExecutiveSummaryPanel.tsx`, `ui/card.tsx`, `ui/table.tsx`) are already on the Stage 2-5 component-pass list, where raw `zinc-*` literals get migrated to semantic tokens — that migration removes this side effect file-by-file as each is visited.

**Amended 2026-09-23 — corrected after a false "done" claim caught in review.** An earlier edit to this note (during the same session) claimed only two small blocks remained unmigrated, based on the Step 5.1 empty-state notes. A targeted grep across every file this redesign has actually touched (`git diff --name-only`, not screenshots — screenshots can't detect this at all, since Stage 1 already remapped the raw zinc *palette* itself, so unmigrated literals render pixel-identical to the semantic tokens) shows that claim understated the gap substantially. Real state of Decision 2's 12-file list, as of 2026-09-23:
- **Fully migrated (0 raw `zinc-*`/`slate-*` utility literals left):** `DataTable.tsx`, `PivotTable.tsx`, `ui/card.tsx`, `ui/table.tsx`.
- **Touched this redesign for other reasons (empty-state fixes, secondary/accent swap, etc.) but the zinc→semantic-token migration itself was never done — still full of raw literals:** `Dashboard.tsx` (~6 sites incl. the hero/upload-view text noted below), `DashboardSummary.tsx` (~60 sites, the entire loaded-state KPI card grid and header controls), `Sidebar.tsx` (~25 sites, effectively the whole component), `KPICard.tsx` (~9 sites), `CommandPalette.tsx` (~21 sites).
- **Never touched by this redesign at all** (not even for the narrower fixes above) — 100% unmigrated: `WelcomeOverlay.tsx`, `AiSettingsModal.tsx`, `ExecutiveSummaryPanel.tsx`.

**User decision (2026-09-23):** don't do the migration now — it's a large, separate diff (5 files' worth of call sites plus 3 untouched files) beyond what a "final verification pass" should absorb unilaterally. Document honestly and track as its own future-pass item, same treatment as the `text-amber-500` sweep below. This redesign's Stage 1-5 work is otherwise complete and visually correct (confirmed via Step 5.3's screenshot pass) — but Decision 2's "shadcn default zinc/slate token references fully replaced" promise is **not** met, and shouldn't be represented as met in any status report on this plan.
7. **DataTable "flagged" (might-be-categorical) badge → Tertiary gold, not amber.** Was `border-amber-400 text-amber-600`. Considered and rejected keeping it distinct: gold now carries two meanings (AI-accent and "worth a second look" data-quality flag), a real semantic-overlap risk if flagged badges get frequent on messy real-world datasets (small-integer-span numeric columns aren't rare — zip codes, years, ratings). Went with gold anyway (user call) because in practice it's bounded to a minority of columns per dataset, which is consistent with "sparse and deliberate" rather than "everywhere." Revisit if flagged badges turn out to fire on most columns in typical real data.
   - **Verified, not assumed:** built a throwaway CSV (`Rating` column, integer 1-5, 10 rows) to actually trigger both the flagged and overridden badge states, read `getComputedStyle` on each in a live browser (not pixel-sampled from a screenshot) — flagged badge computed `rgb(212,175,55)` = `#D4AF37`, overridden badge computed `rgb(124,36,56)` = `#7C2438`. Both bit-exact against the approved hex.
   - **Found and fixed a real bug during that check:** every HSL token in `index.css` `.dark` block had been hand-rounded to whole-number degrees/percent, which was off by 1-2/255 from the approved hex (e.g. Main computed `#7B2438` instead of `#7C2438` — invisible to the eye, but not what was approved). Recomputed all 13 tokens to 4-decimal HSL, verified each round-trips byte-exact via script before writing. Not a one-spot patch — every dark-mode color token in `index.css` was corrected, not just the two in question.

3. **"Minimum" value color (open call from brief):** neutral — Text Secondary, no accent color. Reasoning: gold is specced as sparse/AI-reserved; using it for a plain statistical label (Minimum) alongside a plain-colored Maximum is arbitrary and dilutes the "gold = special" signal the brief itself warns against. The JetBrains Mono numeric treatment already gives Minimum enough visual distinction from body text.
4. **Chart categorical ramp (`--chart-1..5`) — resolved in Stage 4.** Used the `dataviz` skill's validated default categorical theme's dark steps (blue `#3987e5`, orange `#d95926`, aqua `#199e70`, yellow `#c98500`, magenta `#d55181`), not Main/Tertiary — a chart series needs to stay semantically distinct from Main's "active/selected" UI meaning and Tertiary's AI-accent meaning; reusing either as a repeating series color would blur both. Ran `scripts/validate_palette.js` against our actual dark surface `#13151C`: all 5 checks pass (worst adjacent CVD ΔE 8.4 — inside the 6-8 floor band, which the skill requires backing with a legend/direct-label, already how the app's charts work). HSL values carried to 4 decimals per the same exactness standard as the brand tokens.
5. **Inter is not actually wired up today** (no `@fontsource`, no CDN link, no `font-family` override anywhere — Tailwind's default `ui-sans-serif` stack is what's rendering). Treated as "add it now" rather than "already in use," per the brief's intent.
6. **Fonts self-hosted via `@fontsource/inter` and `@fontsource/jetbrains-mono`** (npm), imported in `src/index.css`, not linked from Google Fonts — matches the app's offline-first constraint.
