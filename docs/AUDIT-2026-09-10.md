# DataVista Correctness & Quality Audit — 2026-09-10

Full-codebase audit covering the AST formula parser, window function engine, pivot/query engine, IndexedDB/Dexie persistence, Zustand stores, AI co-pilot integration, statistical engine, and general project health (typecheck, tests, build, lint, e2e coverage, dead code/deps).

Methodology: each module was read in full (not skimmed) by a dedicated reviewer, with claims verified empirically where practical (running the actual parser/aggregation logic against constructed inputs, reproducing crashes with Node, tracing call sites end-to-end). `npx tsc --noEmit`, `npm run test`, `npm run build`, `npm run lint`, `npx depcheck`, and a TODO/FIXME sweep were run directly against the repo.

---

## 1. Prioritized bug list (all modules, severity order)

### Critical

1. **Persistence — data loss on IndexedDB quota exceeded.**
   `src/shared/services/persistenceService.ts:288-289, 358-359, 375-376`
   Dataset/chart/dashboard sync to IndexedDB is `db.X.clear()` followed by `db.X.bulkAdd()` as two separate, un-transacted async operations (no `db.transaction('rw', ...)`). If `bulkAdd` throws — `QuotaExceededError`, tab closed mid-write, any failure — the table is left cleared with nothing written back.
   Concrete scenario: user has dataset A already persisted, uploads large dataset B that pushes the combined payload past the browser's storage quota. `clear()` succeeds, `bulkAdd([A, B])` throws, and dataset A — previously safe on disk — is now gone too. `ChartConfig.data` also carries a full row copy per chart, so the charts table hits the same failure mode at even higher payload. There is no user-facing handling anywhere in the codebase for this: every catch block in `subscribeToStoreUpdates()` is a bare `console.error`, and `grep -rn "QuotaExceeded|quota" src/` returns zero hits. A user can lose previously-saved work with no warning, ever.

2. **Persistence — hydration timeout races its own reentrancy guard, causing a self-triggered destructive rewrite.**
   `src/shared/services/persistenceService.ts:44-48`
   `isHydrating` is cleared via a `setTimeout` while the hydrate `try` block (lines 50-178) may still be running. All write-subscribers guard only on `if (this.isHydrating) return`. On a large dataset, `toArray()` + `evaluateCalculatedFields` + `queryEngine.execute` run synchronously on the main thread (no Web Worker anywhere in the codebase — confirmed via `grep -rli worker src/`). If that work exceeds the timeout, the guard drops mid-hydrate, and hydrate's own `setState` calls fire the write-subscriber, which then `clear()`s and rewrites the table it is still in the middle of reading from. If the rewrite then hits the quota issue above, the dataset being loaded is destroyed by its own load.

3. **Pivot engine — value-field alias collision silently swaps or duplicates displayed numbers.**
   `src/shared/services/pivot/aggregationAdapter.ts:22-24`
   ```ts
   getValueFieldAlias(vf: PivotValueField): string {
     return `${vf.operator}_${vf.column}`;
   }
   ```
   The alias ignores `weightColumn`, `conditionExpression`, and `percentileValue`. The pivot builder UI explicitly supports adding multiple value fields on the same column with different parameters (e.g. two "weighted average of Revenue" fields weighted by different columns). Because `hierarchyBuilder.ts:199` stores aggregation results keyed only by this alias, the second field's result silently overwrites the first in the results map — the UI then renders two distinct-looking columns that both show the same (and for one of them, wrong) number. This also produces duplicate React keys in `PivotTable.tsx`.

4. **Formula engine — `NOT` operator precedence is wrong, breaking a common formula pattern with no error.**
   `src/shared/services/formulaEngine.ts:282-289` (grammar ordering `:217-289`)
   `NOT` is parsed at the same precedence level as unary minus — far above comparison and equality. `NOT [Status] == "Closed"` therefore parses as `(NOT [Status]) == "Closed"`, not `NOT([Status] == "Closed")`. Verified by execution: this expression evaluates to `false` for every row regardless of the actual `Status` value. No parse error, no warning — a calculated column using this (very natural) pattern is silently and permanently wrong.

### High

5. **Window functions & pivot engine — `Math.min(...values)` / `Math.max(...values)` crash on large partitions.**
   `src/shared/services/window/functions.ts:198,212`, and `src/shared/services/queryEngine.ts:476,479` (which the pivot engine also calls into)
   Spreading a values array as call arguments hits the JS engine's max-argument-count limit. Empirically reproduced: `Math.max(...arr)` throws `RangeError: Maximum call stack size exceeded` around 300,000 elements. DataVista's stated target is 100MB files / hundreds of thousands of rows (docs/ADR-001). A MIN/MAX window query, or a pivot value field using min/max aggregated at the grand-total node (which spans the full dataset), throws partway through on a sufficiently large dataset. The pivot UI catches this and falls back to an "Unconfigured" empty state with only a console error — the feature silently disappears rather than failing loudly.

6. **Window functions — O(n²) cumulative/rolling aggregates.**
   `src/shared/services/window/functions.ts:140-213`, `engine.ts:132-146`
   `RUNNING_TOTAL`, `MOVING_AVG`, `WINDOW_MIN`, and `WINDOW_MAX` re-scan the entire frame `[frameStart..frameEnd]` from scratch on every row instead of maintaining an O(n) running accumulator. For the default cumulative frame this is `Σ(idx+1)` = O(n²) total work. Measured directly: a naive O(n²) cumulative sum over 20,000 rows took 404ms versus 1ms for a correct O(n) implementation. At 100k+ rows (realistic for this app's target file sizes) this will visibly hang the UI.

7. **Formula engine — comparison/equality chaining silently produces a nonsense boolean instead of erroring.**
   `src/shared/services/formulaEngine.ts:237-260`
   Both `comparison()` and `equality()` are left-associative `while` loops, so `a < b < c` parses as `(a < b) < c`, with the intermediate boolean coerced for the second comparison. Verified: `5 < 3 < 1` evaluates to `true` even though `5 < 3` is `false`; `1 == 1 == 1` evaluates to `false`. No parse error is raised. Anyone writing a natural range-check formula like `0 <= [X] < 100` gets silently wrong data.

8. **Formula engine — `==`/`!=` use strict comparison, inconsistent with every other operator's type coercion.**
   `src/shared/services/formulaEngine.ts:399-402` (vs. `+` at `:386-390`, which explicitly coerces)
   The tokenizer also maps bare `=` to `==` (`:143`), making this the primary equality UX. Verified: `[Age] == 25` returns `false` when `Age` is the string `"25"` (common after CSV parsing of ragged/inconsistent columns) but `true` when it's the number `25`. Numeric-looking string columns silently fail equality checks with no indication why.

9. **AI co-pilot — an unvalidated LLM response field can blank the entire application.**
   `src/features/ai/summaryEngine.ts:79`
   ```ts
   clean = parsed.summary || parsed.explanation || parsed.title || clean;
   ```
   `parsed` comes from `JSON.parse` on raw LLM output with no runtime shape validation (typed `any`). If the model returns a nested object instead of a string for `summary`, `clean` becomes an object and is later rendered directly by `ExecutiveSummaryPanel.tsx:71`. React throws "Objects are not valid as a React child." `ExecutiveSummaryPanel` has no local `ErrorBoundary` (`Dashboard.tsx:145-153`), so the failure propagates to the app's top-level boundary and blanks the entire dashboard — not just the AI widget — because of one malformed field in an LLM response.

10. **AI co-pilot — unguarded `.alias` access throws a raw JS error to the user.**
    `src/features/ai/aiEngine.ts:123`
    ```ts
    const aggAliases = new Set((query.aggregations || []).map(a => a.alias.toLowerCase()));
    ```
    `query` is LLM-generated JSON cast to a type with no runtime validation. A missing `alias` field (a routine thing for an LLM to omit) throws `TypeError: Cannot read properties of undefined (reading 'toLowerCase')`, which propagates as-is into a user-facing toast (`CommandPalette.tsx:176`, `CalculatedFieldsManager.tsx:89`).

11. **AI co-pilot — no request timeout or cancellation; the UI can hang forever.**
    `src/features/ai/llmService.ts` (every `fetch()` call)
    No `AbortController`, no `signal`, no timeout anywhere (`grep -rn "AbortController" src` → zero hits). A stalled network condition (captive portal, dropped connection, provider hang) leaves `isAiExecuting`/`isGeneratingAi`/`isGeneratingSummary` stuck `true` indefinitely, with no cancel affordance — only a page reload recovers.

12. **Zustand — the `isHydrated` gate that's supposed to show a loading screen is a no-op.**
    `src/store/uiStore.ts:65-73`, `src/features/dashboard/components/Dashboard.tsx:79-81,93`
    Zustand's `persist` middleware (localStorage) sets `isHydrated = true` synchronously in `onRehydrateStorage`, which fires before `Dashboard` even mounts. The real data load — `persistenceService.init()` reading from IndexedDB — only starts in a `useEffect` afterward, but checks the *same* flag. As a result the "Restoring your offline-first dashboard…" loading screen never actually shows: the dashboard renders immediately with empty state, then flashes to populated once IndexedDB hydration resolves. First-visit/welcome-overlay logic can also fire before real data is restored.

13. **Statistical engine — Pearson correlation on a zero-variance column returns `0` instead of null/undefined.**
    `src/shared/services/stats/correlation.ts:26`
    ```ts
    if (denX === 0 || denY === 0) return 0;
    ```
    When a column is constant, correlation is mathematically `0/0` (undefined), not `0` ("no linear relationship"). This is inconsistent with the `n <= 1` branch two lines above, which correctly returns `null` for its own undefined case. Worked example: `x = [5,5,5]`, `y = [1,2,3]` → this code returns `0`; NumPy's `corrcoef` returns `nan`, R's `cor()` returns `NA`. The UI's correlation-matrix coloring treats `0` as "weak/neutral," visually indistinguishable from a genuinely uncorrelated pair, hiding that the value is actually inapplicable.

### Medium

14. **Pivot/query engine — the LRU query cache degenerates to effective capacity 1 above 100k rows, contradicting ADR-003.** `src/shared/services/optimizer/cache.ts:37-45`. ADR-003 documents "a strict limit of 100,000 rows per cache entry," but `set()` only enforces a *total* row cap, and the eviction loop's guard (`this.cache.size > 0`) never runs against an empty cache — so an oversized entry (e.g. 300k rows) is admitted whole. Every subsequent `set()` then finds the total cap already exceeded and evicts everything, including the entry that was just added, before reinserting the new one alone. For any dataset over ~100k rows, both the filter cache and the window/aggregation cache thrash down to holding one entry at a time — no cache hit ever survives a second query.
15. **Pivot engine never uses the query cache at all.** `src/shared/services/pivot/hierarchyBuilder.ts:199` calls `queryEngine.computeAggregations()` directly, bypassing `queryEngine.execute()`'s cache-integrated path entirely. Every pivot configuration change or filter change triggers a full hierarchy rebuild and re-aggregation from raw rows — ADR-003's "near-instant UI feedback" / "eliminates frame drops" claim does not extend to the pivot feature, contrary to what the ADR implies.
16. **Formula engine — `NaN` is not normalized to `null` the way missing values are.** `formulaEngine.ts:677-680` only checks `=== undefined` / `=== ''`, not `Number.isNaN`. `[A] - [B]` on non-numeric strings writes a raw `NaN` directly into the dataset instead of `null`, which can pollute anything downstream that assumes numeric-or-null.
17. **Formula engine — `validate()` never checks function-call argument arity.** `formulaEngine.ts:500-517` only checks that the function name exists, not its arg count against `FunctionDefinition.args`. `IF([A] > 0, 1)` (missing the required third argument) passes validation with zero errors, then silently evaluates to `null` on every row at runtime instead of surfacing a validation error at authoring time.
18. **Zustand — filter changes flood the dashboard's undo/redo history.** `persistenceService.ts:301-315` calls `saveDashboard(id, { settings })` on every `activeFilters` change; `dashboardStore.ts:262-264`'s debounce check only skips debouncing for `layout` updates, so filter-triggered saves push a full snapshot onto the undo stack undebounced. `MAX_HISTORY = 25` fills with filter noise within seconds, evicting genuinely undo-worthy actions like dashboard/KPI creation.
19. **Zustand — executive summary can show stale data after a dataset switch.** `dashboardStore.ts:112-134`'s `generateExecutiveSummary` reads the active dataset at call time but never re-checks it's still active before `set()`-ing the result, and nothing resets `executiveSummary`/`detectedAnomalies` when the active dataset changes. Switching datasets while a summary request is in flight leaves the new dataset's panel showing the old dataset's summary until manually dismissed.
20. **Zustand — `undo()` desyncs dataset/filter context after `loadDashboard`.** The undo snapshot (`dashboardStore.ts:14-18`) only captures `dashboards`/`activeDashboardId`/`activeGlobalFilters`, but `loadDashboard` also mutates `useDatasetStore`/`useFilterStore` directly, which are not captured. Loading a dashboard that switches the active dataset, then undoing, reverts the dashboard id while leaving charts/KPIs showing the newer dashboard's data.
21. **AI co-pilot — architectural, must be disclosed to users.** API keys are stored in plaintext in localStorage (`uiStore.ts:56-64`) and sent directly from the browser to Gemini/OpenAI (`llmService.ts:79,119`). This is an inherent, non-fixable consequence of the zero-backend architecture (ADR-001) and does not need a code fix — but it does need disclosure. More importantly: **ADR-001's stated guarantee "user datasets never leave the browser local storage environment" is factually false once the AI co-pilot is used** — `aiEngine.ts:22-36` sends real sample cell values (not just schema/column names) from the active dataset to Google/OpenAI. This is a documentation/product-disclosure gap, not just an architecture trade-off, and should be corrected in the ADR and surfaced to users at the point of enabling AI features (currently `AiSettingsModal.tsx:158` only says the key is "saved locally," saying nothing about what data leaves the browser).
22. **AI co-pilot — an AI-generated query auto-executes and mutates state with only column-name validation.** `aiEngine.ts:194,201-210` applies the LLM's query result and creates a chart with no user confirmation step (unlike the formula-generation path, which requires the user to review and click Add). `queryEngine.ts:292-293`'s filter evaluation has a `default: return true` for unrecognized operators — an operator the LLM hallucinates or gets wrong silently matches every row, producing a chart titled e.g. "Region = North" that actually contains all regions, with no error surfaced.
23. **Persistence — orphaned rows accumulate forever and can leak into a reused dataset id.** `datasetStore.ts`'s `deleteDataset` never deletes the corresponding `db.filters` row or the `pivotConfig::<id>` entry in `db.uiState` (both are put-only, never `.delete()`d anywhere in the codebase). If a new dataset is later created with the same id, it silently inherits the deleted dataset's stale filter/pivot state.
24. **General — ESLint's `@typescript-eslint/no-unused-vars` rule is explicitly disabled.** `eslint.config.js` sets it to `"off"`. Lint runs clean, but this is not because the codebase has no unused variables/imports — it's because the rule that would catch them is turned off. Lint is present and runs, but is not actually enforcing dead-code hygiene.
25. **General — Playwright e2e coverage is navigation-only, not the real core flow.** `tests/e2e/dashboard.spec.ts` has 4 tests: baseline render, sample-data load, CSV upload with table visibility check, and clicking through Pivot/Stats/Export sidebar tabs to check each view's heading is visible. None of them configure a pivot field, create or verify a chart's actual content, apply a filter and check filtered results, or execute an export and verify a file. The requested upload → filter → pivot → chart → export flow is not exercised end-to-end — only that each screen loads.
26. **General — Gemini API key is sent as a URL query parameter instead of a header.** `llmService.ts:79`. OpenAI's call correctly uses an `Authorization` header (`:119`); the Gemini call appends `?key=...` to the URL, which is more exposed (provider access logs, TLS-inspecting proxy logs, browser devtools network tab, extensions with `webRequest` access) than a header would be. Gemini's API supports an `x-goog-api-key` header as an alternative — worth switching to even though the underlying "key lives in the browser" trade-off is unavoidable.

### Low

27. Statistical engine's variance/standard deviation consistently use the population formula (÷N) everywhere internally, but the UI labels them plainly "Variance"/"Standard Deviation" with no population/sample qualifier, diverging from Excel (`STDEV.S`) and pandas' (`ddof=1`) sample-based defaults with no explanation. (`src/shared/services/stats/descriptive.ts:136-137`)
28. No `^` exponentiation operator exists in the formula grammar at all — the tokenizer throws on it (`formulaEngine.ts:134`). `POWER()` exists as a function, but this is a notable gap for an app presenting itself as Excel-like.
29. No `version`/`migrate` option is set on any persisted Zustand store (`uiStore.ts`, `templateStore.ts`, `viewStore.ts`). Not currently triggered (no persisted shape has changed yet), but there's no migration scaffolding in place for when one does.
30. Several components subscribe to entire Zustand stores with no `useShallow`/`shallow` comparator (`ExecutiveSummaryPanel.tsx:14-21`, `AiSettingsModal.tsx:36`, `OnboardingTour.tsx:6`), causing re-renders on unrelated state changes elsewhere in the same store.
31. `npx depcheck` reports 24 unused dependencies (`react-hook-form`, `zod`, `recharts`, `dexie-react-hooks`, several unused `@radix-ui/*` packages, etc.) and 3 unused devDependencies (`postcss`, `autoprefixer`, `@tailwindcss/typography` — these are likely false positives since Tailwind needs them at build time; verify before removing anything). One missing dependency was flagged: `react-resizable`, referenced in `src/main.tsx` but absent from `package.json`.
32. Production build emits a 1.55MB (474KB gzip) main JS chunk that isn't further split, plus a Vite warning that `AiSettingsModal.tsx` is both statically imported (`CommandPalette.tsx`) and dynamically imported (`Sidebar.tsx`) — the dynamic import can't move it into its own chunk as presumably intended.
33. No `TODO`/`FIXME`/`XXX`/`HACK` comments exist anywhere in `src/` — clean on that front.

## 3. Module-by-module notes (what was checked and cleared)

These were specifically checked and found correct — listed so the audit's negative space is visible, not just the bugs:

- **Formula engine:** unary minus vs. multiplication precedence is correct; circular-reference detection (direct self-reference and mutual A↔B) works correctly via a proper VISITING/VISITED DFS and aborts cleanly rather than infinite-looping; division/modulo by zero explicitly return `null` (not `Infinity`/`NaN`/throw); empty-formula and malformed-input (unclosed parens, trailing operators) cases throw clean, correctly positioned errors; AND/OR short-circuiting and double-negation are correct.
- **Window functions:** RANK/DENSE_RANK tie-skip math is correct standard SQL semantics; PERCENT_RANK and NTILE distribution formulas are correct; frames are correctly scoped per-partition with no state leakage between partitions; LAG/LEAD boundary clipping at partition edges is correctly bounded.
- **Pivot engine:** no key-collision bug — path segments are joined with a NUL separator, so `"ab"+"c"` can't collide with `"a"+"bc"`; no averaging-of-averages bug — every node recomputes every aggregate from its own raw row set rather than from children's pre-aggregated cell values, so subtotal math is a genuine recompute at every level, not a naive rollup; cache invalidation on dataset mutation is correctly wired (though see #15, pivot doesn't use the cache at all).
- **Statistical engine:** mean, median (correctly sorts a copy, doesn't mutate the caller's array; correct odd/even handling), quartiles/IQR (linear-interpolation method, matches NumPy's default), the Pearson correlation formula itself (aside from the zero-variance branch, #13), z-score, and IQR outlier fences (1.5× Tukey fences) are all mathematically correct.
- **AI co-pilot:** no `eval`/`new Function` anywhere in the formula or query engines — the AI-generated-formula path is well defended against prompt-injection-driven code execution (function whitelist, unknown-column check, circular-dependency check, all before execution via a hand-rolled AST evaluator). No API key logging found anywhere in the codebase. No `dangerouslySetInnerHTML` anywhere in `src/`, so even a hostile AI-generated string can't achieve XSS.
- **Zustand stores:** no direct-state mutation bypassing `set()`; no storage-key collisions between the three persisted stores; no genuinely leaked subscriptions (persistence subscriptions are intentionally module-lifetime).
