# DataVista — Product Relevance & Coherence Audit (2026-09-12)

**Scope:** Read-only product review — is DataVista a coherent tool aimed at a real user, not whether the code is correct. Three sibling audits already cover adjacent ground and are not re-litigated here: `AUDIT-2026-09-10.md` (correctness bugs), `AUDIT-TYPE-INFERENCE-2026-09-12.md` (whether computed numbers are semantically meaningful), and `AUDIT-SHELL-COMPLETENESS-2026-09-12.md` (features that look complete but aren't backed by working logic). Where a shell-completeness finding is load-bearing for a product judgment here, it's cited by number, not re-explained. No files were modified for this report.

**Method:** Full pass over the nav/IA (`Sidebar.tsx`, `Dashboard.tsx`, `OnboardingTour.tsx`), README, and every feature module's components/services/stores, tracing what state each screen reads and writes and whether that state is shared, siloed, or partially wired.

---

## 1. Coherent workflow vs. bolted-on features

The honest answer is **uneven, not absent** — DataVista has one real spine (upload → shared `activeDataset` → filter → analyze/visualize) and several modules that plug into it with genuine depth, alongside a couple that visibly don't.

**What's actually connected, and it's the strongest thing in the app:** calculated fields. `datasetStore.ts` re-runs `formulaEngine.evaluateCalculatedFields(dataset)` on every dataset mutation (9 call sites, e.g. `datasetStore.ts:37,41,56,99,122,213,241,272,300`), which writes the computed value directly onto each row (`formulaEngine.ts:769`) and merges a `ColumnMetadata` entry with `role: 'calculated'` (`formulaEngine.ts:831-847`). Because Pivot (`PivotBuilder.tsx:87,93`), Charts (`ChartBuilder.tsx:85,95,103`), Window (`WindowExplorer.tsx:56,61-66`), Stats (`StatsExplorer.tsx:52-58`), and Filters (`FilterPanel.tsx:27-56`) all pick fields from `activeDataset.columns`/`metadata.columns`, a calculated field is indistinguishable from a raw column everywhere. This is exactly the "output of one module feeds another" behavior the product needs, and it works.

**A second real pipeline, but incomplete:** the AI Co-Pilot's natural-language query path is not ephemeral chat output — `aiEngine.executeAIQuery` (`aiEngine.ts:201-234`) runs the LLM's query, pushes results into the shared filter state, and when the model suggests a chart type it calls `chartStore.createChart(...)` directly (`aiEngine.ts:217-231`), which `persistenceService.ts:362-392` then syncs to IndexedDB like any user-built chart. Natural language really can become a saved, durable chart. Likewise `aiEngine.generateFormula` (`aiEngine.ts:239-272`) feeds straight into `CalculatedFieldsManager`'s expression box (`CalculatedFieldsManager.tsx:79-86`) — AI output becomes a real calculated field, not a suggestion you retype. Both are genuine integration points the product review brief explicitly asked about, and both exist.

**What's siloed:**
- **Pivot → Chart: absent in both directions.** `PivotExplorer.tsx`/`PivotBuilder.tsx`/`PivotTable.tsx` contain zero references to charts, and `ChartBuilder.tsx` contains zero references to pivot. There is no "visualize this pivot" action anywhere.
- **Pivot → Stats exists but is thin.** `pivotStore.pivotResult` (`pivotStore.ts:6,8`) is read by a dedicated "Pivot" tab in `StatsExplorer.tsx` (lines 36, 90-128, 457-473), which is a real cross-module pipeline — but it's one-directional and session-only: `persistenceService.ts:262-271` persists `pivotConfig`, not `pivotResult`, so the Stats pivot tab is empty on every reload until the user revisits Pivot first.
- **Window functions never leave the Data Table**, despite looking like a first-class derived column. `windowEngine.augmentMetadata()` (`window/engine.ts:213-258`) registers the column name into `metadata.columns` — so it appears as a selectable field in Pivot/Charts/Stats pickers — but never writes a value into `dataset.data`. Only `DataTable.tsx:171-179` actually calls `windowEngine.execute()`; every other `queryEngine.execute` call site (`FilterPanel.tsx`, `aiEngine.ts`, `ChartVisualization.tsx`, `kpiEngine.ts`, `dashboardStore.ts`) omits `windowQueries`. Select a running-total column in Pivot and you get blank/undefined, not an error (mechanism detailed in `AUDIT-SHELL-COMPLETENESS-2026-09-12.md` #1). Product-level verdict: the intent was clearly full integration (it's built to look like a normal column everywhere), the execution stopped at the Data Table boundary.
- **Each module recomputes its own view rather than sharing one derived-view object**, despite the README calling this a "Unified Query & Pivot Engine" (`README.md:25`). `FilterPanel.tsx`, `DataTable.tsx`, `aiEngine.ts`, and `dashboardStore.ts` each build their own, differently-shaped `Query` and call `queryEngine.execute` independently rather than one module publishing a canonical filtered/derived dataset the others subscribe to. Filtering itself is shared (see §6), but nothing else downstream of it is.

**IA-level symptom of the same problem:** the "Overview" nav item (`Sidebar.tsx:71-75`, described as "Dashboard summary & insights") is actually five different tools stacked on one screen — dataset overview, dashboard/widget editor, undo/redo history, snapshot manager, template save, KPI builder, drill-through modal, and the AI executive-summary banner all live inside `DashboardSummary.tsx` (1 file, 540 lines), reached via a "Switch Dashboard" `<Select>` buried inside the page itself (`DashboardSummary.tsx:296-321`) rather than a nav entry. There is no dedicated "Dashboards" primary nav item — dashboards are a sidebar sub-list (`Sidebar.tsx:405-520`) that changes what the *same* Overview screen renders. A first-time user has no way to guess that clicking "Overview" and clicking a saved dashboard in the sidebar both land on the identical route with wildly different toolbars.

## 2. Redundant or overlapping features

Real overlap exists, and it's not clearly differentiated by depth in the way a well-designed product would signal.

- **Three surfaces show near-identical descriptive stats for the same numeric columns, with no signposting of why you'd pick one over another:**
  - `DashboardSummary.tsx`'s "Data Insights" card shows Average/Maximum/Minimum/Total Sum per numeric column (`DashboardSummary.tsx:427-477`), computed inline (lines 94-135).
  - `StatsExplorer.tsx`'s Descriptive Summaries tab shows the same four numbers plus 13 more (median, mode, variance, stdDev, quartiles, IQR, skewness, kurtosis, unique/missing counts — `stats/descriptive.ts:65-174`).
  - The AI Executive Summary banner (`ExecutiveSummaryPanel.tsx`) narrates outliers computed by `anomalyDetector.ts`, which itself calls `computeOutliers` from the exact same `stats/outliers.ts` module `StatsExplorer`'s Outlier tab uses.
  
  These aren't redundant by accident of scope — Data Insights is a strict subset of Stats, which is defensible as "glance vs. deep-dive" progressive disclosure. But **the computation paths silently diverge on the same label**: on the unfiltered path, `DashboardSummary.tsx:100-106` derives `sum` as `average × count` from cached dataset metadata, while `StatsExplorer`'s `descriptive.ts:122` sums the actual filtered values directly. Both are labeled "Sum" / "Total Sum." With missing values these can disagree, and nothing in the UI hints that "Sum" on the Overview page and "Sum" on the Stats page aren't computed the same way. A user who cross-checks a number between the two screens and finds a mismatch will reasonably stop trusting both.
  - There's also a real coupling, not just visual similarity: `aiEngine.executeAIQuery` overwrites the shared `filteredData` (`aiEngine.ts:214`), and both `StatsExplorer` and `DashboardSummary`'s insights memo read that same slice. Running one `/ai` query silently redefines what two unrelated-looking screens display next.
- **KPI cards are genuinely differentiated, not redundant** — one metric, one aggregation, optional trend/sparkline/conditional formatting, meant as a persistent dashboard widget (`kpiEngine.ts:12-104`, `KPICard.tsx`). This is the one case in the app where "three ways to see a number" is actually "three different jobs" (glance tile, deep analysis, curated dashboard metric) and it holds up.
- **Filters have three non-overlapping mechanisms for what a user experiences as one concept** (detail in §6) — this reads as redundant plumbing rather than intentional layering, since nothing in the UI explains why Window Functions ignore the Filters page while everything else obeys it.

## 3. Missing features a comparable tool would be expected to have

Given the depth already present (AST formula engine, pivot, window functions, AI copilot), a user coming from Excel/Sheets/Tableau/Power BI will notice these gaps immediately:

- **No way to join or relate two datasets.** Verified by grep and by reading every hit: `Array.prototype.join()` calls, `filterManager.merge()` (which merges *filter/query objects*, not rows — `filterManager.ts:8`), and `schemaDiff.ts` (which diffs two *versions* of the same re-uploaded dataset, not two different datasets). `useDatasetStore` holds multiple independent datasets, but nothing combines rows or columns across them. The closest thing is `GlobalFilter.linkedDatasets` (`filter.ts:9`), which broadcasts one column-value filter to other datasets sharing that column name — filter propagation, not a join. For a tool whose sidebar treats "Datasets" as a first-class multi-item list, the inability to relate two of them is the single most conspicuous gap next to what's already built (a formula engine and pivot table both assume single-table input by construction).
- **No way to get a dashboard or view in front of someone who doesn't have the file.** Every export (`ExportPanel.tsx`) is a local file download — filtered CSV, per-chart PNG/SVG, a PDF report (`exportUtils.ts:41-260`). "Workspace Snapshots" (`snapshotStore.ts:7-24`) and Templates (`templateStore.ts`) both persist to `localStorage` only, with no export/import of that state as a file. There is no way to hand a colleague a `.json`/`.dvista` workspace file, let alone a link. This is a defensible, statable limitation of an offline-first architecture (no backend to host a shareable view) — but it's currently an *unstated* one; nothing in the README or app frames "everything stays trapped in this browser tab" as a tradeoff, and a trivial partial fix (export/import the whole workspace as one JSON file) is conspicuously absent given how much granular export already exists.
- **No scheduled/recurring anything** — expected and correctly out of scope for a client-side tool, and unlike the two gaps above, this one doesn't need fixing or even a callout; it's an inherent, unsurprising consequence of the "no backend" premise the README leads with.
- **No lookup/VLOOKUP-equivalent formula function** — the formula library covers math/string/logical/date functions (`formula/library/*`); grepping it for `vlookup|index_match|lookup|xlookup` returns exactly one hit, a comment describing the function registry's own case-insensitive name lookup (`formula/library/registry.ts:17`), not a user-facing function. Combined with the no-join gap above, there is no way to enrich one dataset with values from another at all, at any layer (formula, pivot, or dataset-level).
- **No pivot-to-chart pipeline** (see §1) — for a tool that leads with pivot tables in its README screenshot gallery, the absence of "visualize this pivot" is a bigger miss than it would be in a pivot-only tool, precisely because Charts is right next to it in the nav with 8 chart types ready to receive data.

## 4. Value proposition clarity

The README's positioning is specific and good on paper: "an offline-first, browser-native BI platform" where "your data never leaves your machine" (`README.md:8,15`). That's a real, differentiated niche — it's the correct pitch for this codebase's actual architecture (IndexedDB/Dexie, no backend, confirmed by `ADR-001-Zero-Backend-Architecture.md`).

**It is contradicted by the AI Co-Pilot feature, in the same document.** `README.md:26` markets "AI Co-Pilot Integration: Connects directly to LLM APIs (Google Gemini, OpenAI GPT-4o) for natural language data querying." Tracing what actually gets sent: `aiEngine.buildContext()` (`aiEngine.ts:21-57`) includes `sampleValues` per column (`types.ts:8`, populated at `aiEngine.ts:31,50`) inside `AIPromptContext`, and `llmService.ts`'s `contextMessage` (built at line 92, embedding `Available Columns: ${JSON.stringify(context.columns)}` — which carries those sample values) is sent as the POST body to `generativelanguage.googleapis.com` in the Gemini branch (`llmService.ts:100-133`) or `api.openai.com` in the OpenAI branch (`llmService.ts:134-160`). **Real values from the user's uploaded dataset leave the machine the moment an API key is configured and a natural-language query or AI formula is run** — verified first-hand, not inferred. Nothing in `AiSettingsModal.tsx` discloses this: the only related copy is "Key saved locally in offline browser storage" (`AiSettingsModal.tsx:158`), which is about the *key*, not the *query data*, and is easy to misread as covering both. This is the sharpest finding in this review: a portfolio reviewer or careful user who reads the README's headline privacy claim and then configures an API key gets a materially different privacy posture than promised, with no in-app warning at the point of consequence (typing the query, not just setting the key).
- **Secondary overpromising, lower stakes:** README:110 claims charts have "customizable color schemes" — no such control exists; `ChartVisualization.tsx` hardcodes a fixed 5-color palette at all 4 use sites (already flagged as a minor note in `AUDIT-SHELL-COMPLETENESS-2026-09-12.md`, cited here only because it compounds the pattern of the README being slightly ahead of the product).
- **What's accurate and worth crediting:** the "8 interactive visualization types" claim (`README.md:110`) is exactly right (bar/line/pie/scatter/histogram/heatmap/area/bubble, each independently implemented). The 100MB upload limit is genuinely enforced (`FileUpload.tsx:31-39`), not just a docs claim — though the in-app dropzone label itself says "up to 10MB" (`FileUpload.tsx:209`), an internal inconsistency between the app's own copy and its own logic, independent of the README. The "14-step guided tour" claim is exact — `OnboardingTour.tsx` has precisely 14 `Step` entries, and every target resolves to a real element.
- **A quieter clarity problem:** the tour's 14 steps never target `[data-tour="dataset-grid"]` — the Data Explorer nav item is assigned that tour attribute in `Sidebar.tsx:286` but no step in `OnboardingTour.tsx` references it. The tour walks a first-time user past Overview, Upload, Filters, Statistics, Window Functions, Export, Charts, Pivot, and Search, but skips the one screen that houses calculated fields and AI-assisted formula generation — arguably the deepest, most differentiated single screen in the app.

## 5. Feature depth vs. breadth

**Genuinely deep, in order:**
1. **The AST formula engine + calculated fields.** Not just present but load-bearing: every module reads through it (§1), it's independently verified against non-ASCII columns, duplicate names, empty datasets, and 150-column-wide inputs (`AUDIT-SHELL-COMPLETENESS-2026-09-12.md`, "Verified NOT shells"), and it's the one place the AI co-pilot's output is durably absorbed into the rest of the app rather than displayed and discarded.
2. **Statistics (`StatsExplorer.tsx`, `stats/*`).** Four real tabs — descriptive (17 metrics), Pearson correlation matrix, IQR/Z-score outlier detection with adjustable threshold, and a pivot-slice variant — backed by a stats engine that correctly returns `null` rather than a misleading `0` for zero-variance correlation. This is the module that most looks like it was built by someone who has actually done statistical analysis, not just wired up formulas.
3. **KPI cards.** Small in surface area but fully thought through end-to-end: trend computation against a real prior period, polarity-aware coloring, sparklines, conditional formatting, and drill-through to raw rows — all genuinely wired (confirmed in `AUDIT-SHELL-COMPLETENESS-2026-09-12.md`'s verification pass).

**Shallow relative to the rest of the app:**
- **Window Functions.** Looks like a first-class SQL-style feature (13 function types, custom frames, partitioning) but is architecturally a dead end outside the Data Table (§1) — the depth is in the computation engine, not in the feature's place in the product.
- **Templates.** Exactly one built-in template (`template-sales-overview`, hardcoded to `Region`/`Sales`/`Profit`) — real and domain-specific in content, but a single example is closer to a demo than a feature; and it's currently structurally broken relative to the live `KPICardConfig` shape. `KPICardConfig` requires `primaryMetric: {column, aggregation}`, `sparkline: boolean`, and `datasetId` (`kpi/types.ts:3-18`), but the built-in template's KPI objects only set flat `metricColumn`/`aggregation`/`polarity` fields (`templateStore.ts:52,59`), and `templateEngine.extractTemplate`'s schema-extraction reads the same nonexistent `kpi.metricColumn`/`kpi.trendDateColumn` (`templateEngine.ts:29-30`) — a no-op against real KPI objects. `npx tsc -p tsconfig.app.json --noEmit` confirms this is a live type error, not a hypothetical: `TS2353` on `templateStore.ts:52` and `:59` ("'metricColumn' does not exist in type 'KPICardConfig'") and `TS2339` on `templateEngine.ts:29` and `:30`. (The project's bare `npx tsc --noEmit` reports nothing because the root `tsconfig.json` has an empty `files` list and only references sub-projects; `-p tsconfig.app.json` is the config that actually type-checks `src`.) A "genuinely tailored" template that doesn't actually type-check against the feature it configures.
- **AI Co-Pilot's discoverability.** The functionality itself (query→chart, prompt→formula) is real (§1), but its *product surface* is a single Sparkles icon in the header that opens only an API-key settings modal (`Sidebar.tsx:195-211`, `AiSettingsModal.tsx`) — the actual "ask AI a question" entry point is a `/ai` prefix typed inside the global Cmd+K command palette (`CommandPalette.tsx:90-91`, placeholder text at line 300: `"Type '/ai ...' for AI Co-Pilot, or search commands, datasets..."`), and AI-formula generation is a secondary input buried inside the Calculated Fields modal (`CalculatedFieldsManager.tsx:79`). For a feature the README leads with as a headline capability, it has no dedicated screen and no obvious affordance — a new user clicking the star icon that's literally labeled for the AI Co-Pilot will find only settings, not the co-pilot.
- **Export.** Broad-looking (CSV, PNG, SVG, PDF) but the PDF/PNG/SVG paths are documented elsewhere as non-functional in the default flow (`AUDIT-SHELL-COMPLETENESS-2026-09-12.md` #3, #5) — not re-litigated here, but relevant to depth-vs-breadth: Export reads as more capable than it is.

## 6. Internal consistency of design language and interaction patterns

**Filtering: three separate mechanisms for one user-facing concept.** The standalone Filters page (`FilterPanel.tsx`) writes to `useFilterStore`, consumed by Charts, Pivot, Stats, Export, and the Data Table. A second, independent mechanism — `dashboardStore`'s `activeGlobalFilters` plus `filterManager.merge()` — governs Charts/KPI cards specifically *inside* a named Dashboard, and supports cross-dataset propagation via `linkedDatasets` that the standalone Filters page has no equivalent of. `WindowExplorer.tsx` imports neither store and reads `activeDataset` directly — Window Functions run over the full unfiltered dataset while every other analysis screen (correctly, per its own "Filtered View Active" banner in `PivotExplorer.tsx:121-124` and `StatsExplorer.tsx:649-652`) operates on the filtered subset. A user who filters the dataset, then opens Window Functions expecting the same subset they just saw in Stats, silently gets different rows. Compounding this, the standalone Filters page's own README-promised numeric-range and "contains" controls don't exist there — that functionality only exists in the dashboard-scoped `GlobalFilterBar` (mechanism detailed in `AUDIT-SHELL-COMPLETENESS-2026-09-12.md` #6) — so the page users are told to visit first for filtering is the least capable of the three filter surfaces.

**Loading/empty/error states are hand-rolled per module, not shared components.** There is no `Skeleton` component anywhere in the codebase (confirmed absent from `shared/components/ui`), so no module shows a skeleton loader during recomputation — the only loading treatment is one global full-view spinner gated by `useUiStore.isLoading` in `Dashboard.tsx`. Empty states are copy-pasted `<div className="text-center py-12">` blocks with near-identical text in Filters, Charts, Export, and DataTable, but Window Functions uses a structurally different pattern (`WindowExplorer.tsx:76-80`, a centered `h-[50vh]` flex column with a different icon) — not a deliberate variant, just independent authorship. `ErrorBoundary` coverage is uneven: the app root, Sidebar, three lazy-loaded view containers (Pivot/Stats/Window, but not Charts/Filters/Export/DataTable), and two AI components are wrapped; Filters, Export, and the Data Table have no error boundary anywhere in their tree.

**Terminology is more disciplined than the "field vs. column vs. attribute" framing suggests, but still undocumented.** "Column" is the universal base noun (`Dataset.columns`, used pervasively — 30-40+ hits per major module). "Field" is not used as a loose synonym; it's consistently narrowed to two specific things: pivot value fields (aggregation outputs) and `CalculatedField` (formula-derived columns). "Dimension" is likewise narrowed to pivot row/column axes and the `ColumnMetadata.role` enum — it doesn't leak into Charts/Stats/Filters vocabulary. "Attribute" isn't used as a data-modeling term anywhere (every hit is React's `HTMLAttributes`). So the four words aren't interchangeable, which is better than the brief's premise suggested — but there's no glossary anywhere in `shared/types`, and a user moving from Filters ("column") to Pivot ("dimension"/"field" mixed with "column") to the Calculated Fields modal ("field") still meets three different nouns for what they'll mentally model as one concept, with nothing in the UI explaining the distinction is intentional rather than sloppy.

## 7. Who is this actually for, and does the app know it?

The app is built by and for someone comfortable with formulas and pivot logic — that's where the real engineering investment is (§5) — and the AI co-pilot reads as a bolted-on second audience rather than a first-class alternative path for a non-technical user. The evidence:

- The AI path *can* replace formula-writing (NL → formula, NL → query+chart) and genuinely produces durable output (§1) — in principle this is exactly the "progressive disclosure" story the brief asks about: casual users type a sentence, power users write `[Revenue] - [Cost]`.
- In practice it doesn't read that way, because the AI entry points are hidden behind power-user affordances: a keyboard-shortcut command palette (`⌘K` then typing `/ai `) and a secondary button inside a formula-editing modal. A non-technical user — the person who'd most want to type a sentence instead of a formula — is the least likely to discover Cmd+K exists, let alone that typing `/ai` inside it does something different from every other keystroke there.
- There is no default, visible "ask a question about your data" surface anywhere in the primary nav or on the Overview screen, despite Overview being the one screen crowded with everything else (undo/redo, snapshots, templates, KPI builder — §1). The one AI element that *is* always visible on Overview, the Executive Summary banner, is read-only and non-conversational — it tells you something, but you can't ask it anything back from where you're looking at it.
- Net assessment: this is not "one tool serving two audiences well," it's one tool built for the formula/pivot audience with a real but under-surfaced natural-language capability attached. A non-technical user who never opens Cmd+K will conclude, correctly given what they can see, that DataVista is a power-user tool with an AI settings icon that does nothing until you type formulas manually.

## Top 3 highest-leverage changes

1. **Fix or disclose the AI privacy contradiction (§4).** This is the one finding where the product's stated core differentiator ("your data never leaves your machine") is directly falsified by traced, verified code (`llmService.ts`, `aiEngine.ts:buildContext`) the moment a real feature is used — everything else in this review is a coherence or polish gap, but this one is a trust gap, and it's cheap to fix: a one-line in-app notice at the point of typing an AI query/formula ("query text and sample values are sent to Gemini/OpenAI") plus a README caveat costs almost nothing and removes the single claim that would make a careful reviewer distrust the rest of the document.
2. **Give the AI Co-Pilot a real, visible entry point (§5, §7).** The functionality already works end-to-end (query→chart, prompt→formula) — the header's Sparkles icon just needs to open the actual co-pilot instead of only settings, or the Overview screen needs a persistent "Ask" box. This is the highest-leverage *product* fix because it's a UI-routing change, not new engineering, and it resolves the "does the app know who it's for" ambiguity in §7 directly.
3. **Materialize window-function columns into real data, or stop presenting them as normal columns elsewhere (§1, §5).** Right now the product actively invites a broken workflow: it lists window columns as selectable fields in Pivot/Charts/Stats pickers, and picking one silently returns blank data. Either compute the value once and store it (matching how calculated fields already work, which is the app's own best pattern) or filter window-derived columns out of every picker outside the Data Table until that's done — either fix removes a "looks finished, isn't" trap that undercuts confidence in the rest of the analytical engines, which are otherwise the strongest part of the app.
